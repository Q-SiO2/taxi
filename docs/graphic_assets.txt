TaxiMobile — Graphic Asset Production Requirements
===================================================

PURPOSE
-------
This file lists the custom graphic assets that should be created for the TaxiMobile passenger and driver applications.

The goal is to avoid relying on mismatched stock icons, random emoji, generic illustrations, inconsistent vehicle renders, or assets with incompatible perspective.

Brand palette:
- White: #FFFFFF
- Navy: #0B1F3A
- Secondary navy: #163A63
- Mustard yellow: #D6A800
- Light mustard: #F3D76A
- Deep navy: #071426

GENERAL RULES
-------------
1. All assets must belong to one visual family.
2. Vehicle renders must share the same camera angle.
3. Lighting direction must be consistent.
4. Shadows must be consistent.
5. Stroke width must be consistent for vector icons.
6. Avoid tiny details that disappear at mobile scale.
7. Design at high resolution, then export required sizes.
8. Keep master files editable.
9. Prefer SVG for flat vector illustrations/icons.
10. Prefer transparent PNG/WebP for rendered vehicle assets.
11. Keep source 3D models if 3D renders are used.
12. Avoid baking text into images.
13. Do not bake localized labels into graphics.
14. Export light-background-safe assets by default.
15. Test every asset at actual UI size before final approval.

====================

- Standalone app symbol

  - SVG

  - PNG transparent 1024x1024

A02. Full wordmark

- Horizontal version
- Dark/navy version for white backgrounds

A03. App icon

A04. Splash logo

- No baked background
- Transparent SVG/PNG

D. TAXI VEHICLE MAP MARKERS
===========================

IMPORTANT:
Do not use random car icons from different sets.

All vehicle marker assets must:
- point upward at 0 degrees in the source image
- have transparent backgrounds
- use the same visual projection
- use consistent shadow/no-shadow policy
- have a known anchor
- be readable at approximately 32–48 dp

D01. Standard city taxi — top-down
Recommended:
- nearly top-down
- slight isometric depth permitted
- strong roof silhouette
- mustard body or mustard accent depending on real service branding requirements

Exports:
- 128x128
- 256x256
- 512x512 transparent PNG/WebP
- vector only if visual quality remains strong

D02. Large/shared taxi — top-down
Must visibly differ from standard taxi:
- larger body
- van/MPV/sedan form as appropriate
- distinct roof/cabin silhouette

D03. Intercity taxi — top-down
If visually distinct from shared taxi:
- separate asset
Otherwise use same vehicle geometry with a clear service badge outside the vehicle asset.

D04. Selected standard taxi
Options:
- same vehicle with programmatic halo preferred
- avoid creating unnecessary duplicate files

D05. Selected large taxi
Same rule.

D06. Driver-offline vehicle marker
Only if driver app visually shows own vehicle differently.
Prefer programmatic opacity/status ring.

E. SERVICE SELECTION VEHICLE RENDERS
====================================

These are NOT the same as map markers.

Use a controlled 3D or high-quality isometric render set.

CAMERA SPEC
-----------
Recommended camera:
- shallow 3/4 front-side or shallow isometric
- camera height and focal length locked for every vehicle
- vehicle faces the same direction
- same framing
- same ground plane
- same scale relationship

LIGHTING SPEC
-------------
- large soft key light from upper-left
- mild fill from opposite side
- subtle contact shadow
- white/transparent background
- no dramatic reflections
- no nighttime environment maps

E01. Standard city taxi hero render
Use:
- service picker card
- booking confirmation
- optional landing composition

Exports:
- transparent PNG/WebP
- 1024 px longest side master export
- 512 px UI export
- 256 px UI export

E02. Large/shared taxi hero render
Must be proportionally larger and clearly distinct.

E03. Intercity taxi hero render
Only if materially different.

E04. Vehicle silhouette fallback
Flat navy/mustard vector version for:
- low-bandwidth mode
- skeleton/loading
- compact cards

R. ILLUSTRATION STYLE GUIDE
===========================

All illustrations should share:

Geometry:
- clean
- moderately geometric
- not childish
- slightly simplified

Stroke:
- 1 consistent family
- navy outlines where used

Palette ratio recommendation:
- 65–75% white/negative space
- 15–25% navy
- 5–15% mustard
- semantic colors only where required

Shadows:
- soft
- subtle
- cool-neutral
- no heavy black drop shadows

Perspective:
- flat or shallow isometric
- never mix flat people/icons with photoreal cars on the same illustration

People:
- if used, keep neutral and simplified
- avoid unnecessary detailed facial features
- ensure cultural context feels natural for Morocco without caricature

S. 3D MODEL REQUIREMENTS
========================

If actual runtime 3D cars are eventually used:

Create/source:
- one standard taxi model
- one large/shared taxi model
- optional intercity variant

Requirements:
- low-poly/mobile appropriate
- clean topology
- PBR materials
- separate body material for recoloring
- wheel geometry optimized
- origin centered properly
- forward axis documented
- scale in real-world units
- LOD versions if required

Suggested deliverables:
- `.glb` master runtime export
- source `.blend` file or original modeling file
- texture maps
- 1K textures maximum initially unless visual testing proves higher resolution necessary

Important:
Runtime 3D should only be adopted if it produces a real UX benefit.
For map markers, pre-rendered top-down assets are usually cheaper and more predictable.

W. QUALITY CONTROL CHECKLIST
============================

For every final asset verify:

[ ] It uses the approved palette.
[ ] It looks correct on white.
[ ] It remains readable at target mobile size.
[ ] It has no accidental transparent padding.
[ ] The anchor point is documented for map markers.
[ ] Vehicle forward direction is documented.
[ ] Perspective matches sibling vehicle assets.
[ ] Lighting matches sibling renders.
[ ] Stroke weight matches the icon family.
[ ] No text is baked into localized graphics.
[ ] No trademark is recreated improperly.
[ ] Export file is optimized.
[ ] Source file is preserved.
[ ] Naming convention is correct.
[ ] Dark/navy background version exists where necessary.
[ ] Asset has been tested inside the real Compose UI.

X. MOST IMPORTANT VISUAL WARNING
================================

Do not solve a layout problem with artwork.

If:
- proportions are wrong,
- sheet height is wrong,
- spacing is wrong,
- typography hierarchy is wrong,
- input behavior is wrong,
- map camera padding is wrong,
- marker anchoring is wrong,

then replacing assets will not fix the screen.

Assets should strengthen an already-correct interface.

The correct workflow is:
1. Define screen behavior.
2. Define layout.
3. Define component sizing.
4. Define interaction states.
5. Add approved placeholder geometry.
6. Produce final artwork to those exact dimensions.
7. Integrate.
8. Test at actual device sizes.
